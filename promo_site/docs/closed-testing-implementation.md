## 공통 설정

`lib/site-release.ts`가 공통 해석 기준이다. 환경변수는 `.env.example`에 설명되어 있다. Netlify에서는 **빌드와 Functions 양쪽 범위**에 같은 값을 설정하고 재배포한다. 열린 홈페이지는 공통 설정 API를 조회하고, 서버는 제출 시 다시 검사한다.

| 설정 | 기본값 / 동작 |
|---|---|
| `RELEASE_STATUS` | `recruiting` / `testing` / `reviewing` / `released` |
| `ACCEPTING_TESTERS` | 모집 단계 기본 true, 다른 단계 기본 false. 추가 모집을 독립 제어 |
| `TESTER_MINIMUM_PARTICIPATION_DAYS` | 14일 |
| `NEXT_PUBLIC_GOOGLE_PLAY_URL` | 실제 Play 다운로드 주소가 없으면 다운로드 버튼 미표시, released 대신 reviewing |
| `TESTER_BENEFIT_CONFIRMED` | 운영자가 확정한 기본 혜택은 표시. false 설정 시 비노출. 별도 문구를 쓰려면 true로 명시 승인 |
| `TESTER_BENEFIT_TEXT` | 미설정 시 확정된 평생 혜택·광고 없음·자체 제공 AI 제외 문구 사용 |
| `TESTER_PRIVACY_CONFIRMED` | false. 기간·실제 문의 이메일도 있어야 접수 허용 |
| `TESTER_RETENTION_DAYS` | 미설정. **신청일부터** 계산하는 보관 일수이며 테스트 종료일부터가 아님 |
| `TESTER_PRIVACY_NOTICE_VERSION` | 안내문 변경 시 갱신. 동의 기록에는 실제 보관 일수·참여 기간도 함께 표시 |
| `NEXT_PUBLIC_SUPPORT_EMAIL` | 기존 공개 문의 설정 재사용. 예시 주소로 수집 활성화 불가 |

보관 기간·문의 주소는 확정 답변이 없어 실제 수집을 활성화하지 않았다. 현재 미리보기에서는 모집 안내와 신청 창을 확인할 수 있지만 제출은 비활성화된다. 보관 기간을 ‘테스트 종료 후’ 기준으로 운영하려면 그 기준을 별도로 확정하고 구현도 함께 조정해야 한다. 2026-11-27 후속 요청에 따라 Android 기기·Google 계정으로 누구나 테스트를 신청할 수 있다고 안내하며, 어린이는 Family Link 등 계정 설정에 따라 보호자 동의가 필요할 수 있다고 표시한다.

## 신청·보관·운영

서버: `netlify/functions/tester-applications.mts` → `lib/tester-service.ts` / `lib/tester-endpoint.ts`. 기존 의견 게시판과 같은 Netlify Blobs 기반이지만 **별도 비공개 저장소** `memorize-tester-applications`를 사용한다. 신청 데이터는 공개 HTML·클라이언트 번들·설정 API에 포함하지 않는다.

- Google 계정 이메일은 Gmail로 제한하지 않는다. 사용 목적은 선택, 참여 확인·개인정보 동의는 필수다. 선택 동의의 초기값은 false다.
- 서버 시각·동의 버전·운영 상태·보관 만료 시각을 기록한다. 이메일의 HMAC 기반 키와 원자적 생성으로 중복 저장을 방지한다. 중복 여부를 공개 응답에 노출하지 않고 기존 동의를 덮어쓰지 않는다.
- Origin·본문 형식·이메일·필수 동의·현재 안내문·모집 상태를 서버에서 검증한다. 허니팟과 요청 제한을 적용한다. 원문 IP를 신청 데이터에 저장하지 않는다.
- 저장 실패 시 성공 응답을 만들지 않는다. 클라이언트는 입력을 유지하고 다시 시도할 수 있게 한다. 이메일 자동 발송은 구현하지 않았다.
- 보관 일수 도래 후 시간당 정리 함수 `tester-retention`이 삭제한다. 관리자 조회 시에도 기한이 지난 신청은 제거한다. 출시 알림 동의에도 같은 보관 기한을 적용한다.
- Netlify의 예약 함수는 정식 게시 배포에서 예약 실행되므로 배포 후 실행 여부를 확인해야 한다. 미리보기 배포에서는 수동 실행으로 검증해야 한다. [Netlify 공식 문서](https://docs.netlify.com/build/functions/scheduled-functions/)

통합 관리 화면은 `/admin`이다. 기존 `/tester-admin`은 새 주소로 이동한다(Netlify 배포에서는 301, 로컬에서는 클라이언트 이동 및 대체 링크). 공개 의견 게시판에서 관리자 로그인 UI를 제거하고, 이 화면에서 한 번 로그인한 뒤 ‘테스트 계정 관리’와 ‘의견 게시판 관리’를 전환한다. 기존 관리자 비밀번호·서명 쿠키를 공유한다. 세션 확인은 신청 저장소 접근과 분리했고, URL의 비공개 여부에 의존하지 않고 목록·변경·삭제 및 게시판 관리 API에서 인증을 확인한다. 관리자 로그인 전에는 신청 데이터가 반환되지 않는다. 신청 상태 변경·삭제와 게시판 처리 상태 변경·운영자 답변·삭제 기능을 유지한다. 테스트 계정 관리는 홈페이지 신청·출시 알림 계정에 대한 것이며, 앱 회원·Play Console 테스터 목록·평생 혜택 권한과 자동 연동되지 않는다.

운영 순서는 신청 확인 → Play Console 계정 등록 → 참여 링크 수동 이메일 안내 → 운영 상태 변경이다. 출시 알림은 동의한 계정에만 발송하고 목적이 끝난 정보는 삭제한다. Play Console에 별도로 등록한 목록·수동 발송 메일에도 실제 개인정보 운영 정책을 적용해야 한다. 신청 정보만으로 실제 opt-in이나 연속 참여 기간을 추정하지 않는다. 적용 인원·기간은 운영자 계정의 Play Console에서 확인한다.

## 실행한 검증과 제한

- `npm run test:testing`에 해당하는 Node 24 테스트: **11개 통과**. 상태 전환, 맞춤 이메일 도메인, 동의, 동시 중복, 서버 접수 차단, 비인가 조회·변경 차단, 관리자 상태·삭제, 요청 제한, 저장 실패, 만료 정리, 관리자 서명 위변조와 저장소에 접근하지 않는 공통 관리자 세션 확인을 포함한다.
- 신규 기능 파일 ESLint: 통과.
- `vinext build`: 통과.
- Netlify 정적 빌드: 컴파일·TypeScript·12개 정적 페이지 생성을 통과했지만 최종 단계에서 기존 Next.js 16.4.2의 `SecurityFatalError`가 발생했다. 동일 빌드 재시도에서도 반복되어 **최종 빌드 성공으로 보고하지 않는다**. 보안 업데이트 검토 후 배포 빌드를 다시 확인해야 한다. 자동 업그레이드나 보안 검사 우회는 하지 않았다.
- 기존 `tests/rendered-html.test.mjs`: 일반 Node 실행 시 기존 `cloudflare:workers` 모듈 로더 오류로 3개 실행 실패. 이를 기능 회귀 성공으로 간주하지 않았다. 대신 실제 로컬 서버에서 `/`, `/ai-api`, `/feedback`, `/privacy`, `/account-deletion`, `/tester-admin`, 설정 API의 200 응답과 비인가 신청 목록의 401 응답을 확인했다.
- 공개 배포·Play Console 등록·실제 안내 메일 발송·실제 신청 개인정보 수집은 수행하지 않았다. 배포 후 테스트 계정으로 저장·중복·관리자 조회·삭제 및 예약 함수 실행을 확인해야 한다.

## 운영자가 확정·준비할 항목

1. 개인정보 문의 이메일과 **신청일부터 계산할 보관 일수**를 확정한다. 수집·국외 처리 등 운영상 필요한 개인정보 고지사항도 실제 서비스 운영에 맞춰 확인한 뒤 `TESTER_PRIVACY_CONFIRMED=true`로 전환한다.
2. Next.js 보안 경고를 해결하고 Netlify 배포 빌드·Functions 저장소·시간당 정리 실행을 검증한다.
3. Play Console의 실제 적용 조건·테스트 트랙·참여 링크·수동 이메일 안내 절차를 준비한다.
4. 정식 출시 시 실제 다운로드를 확인한 다음 Play 주소와 출시 상태를 변경한다. 확정된 테스터 혜택을 앱에서 계정별로 부여·복원하는 권한 로직은 별도로 구현·검증해야 한다. 이번 변경은 홈페이지의 공통 설정과 안내 문구에 대한 것이다.
